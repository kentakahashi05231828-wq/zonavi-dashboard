# ZONAVI 利用状況ダッシュボード

東京造形大学の学生向けアプリ **ZONAVI**（iOS）の利用状況を可視化する、静的ウェブダッシュボードです。
ビルド不要のバニラ ES モジュールのみで構成し、Firebase Realtime Database に保存された
匿名の集計カウンタを読み出してグラフとして表示します。

## デモ

Firebase に接続せず、サンプルデータで画面を確認できます。

```
index.html?demo=1
```

## 画面の内容

画面は上から下へ「実データ → まとめ」の順に並びます。

| セクション | 内容 |
| --- | --- |
| サマリー | 選択期間の KPI。増減は直前の同じ長さの期間との比較 |
| ユーザー数（実人数） | 累計ダウンロード、WAU / MAU、粘着度。週12本・月6本の推移 |
| 日別の推移 | アクティブ端末数・セッション数などの折れ線 |
| タブ別の使われ方 | 予定 / ホーム / リンク / 設定 の表示回数 |
| 機能別の利用回数 | タブごとにまとめた、実際に押された機能の**回数** |
| 機能ごとの利用者数 | 何台がその機能を使ったかの**人数**。1端末1日1カウント |
| ウィジェット | 追加率、どの種類が置かれているか、設置場所とサイズ、1端末あたりの設置数 |
| 時間帯別の利用 | 1 日のどの時間に使われているか |
| 曜日別の利用 | 授業のある平日と休日の差 |
| 利用環境の内訳 | 機種・アプリ/iOS バージョン・画面サイズ・通知許可・言語・表示モード・利用期間 |
| 全データ表 | グラフの元データ。CSV でダウンロード可能 |
| レポート（自動分析） | 上のデータを期間比較でまとめ、次の一手まで文章にする（最下部） |

表示期間は 7 / 14 / 30 / 90 日、データソースは本番（`analytics`）と開発（`analyticsDebug`）を切り替えられます。
ライト / ダークの表示モードにも対応しています。

## 「延べ」と「実人数」の違い

利用者数にも 2 通りの数え方があります。

- **延べ**（`daily/<日>/summary/activeUsers`）— 1 端末 1 日 1 カウント。
  同じ人が週に 5 日開けば 5。日ごとの推移を見るのに向いています。
- **実人数**（`weekly/<週>/activeUsers`、`monthly/<月>/activeUsers`）— 1 端末 1 週（1 月）1 カウント。
  同じ人が週に 5 回開いても 1。「何人に使われているか」はこちらです。

日別の延べを足しても実人数にはなりません（同じ端末が何日も数えられるため）。
そこでアプリ側で「その週・その月で最初に開いたときだけ 1 を足す」処理を持ち、
`weekly` / `monthly` ノードに分けて保存しています。

週は ISO 8601（月曜はじまり、JST）です。アプリ側 `AnalyticsService.weekKey` と
ダッシュボードの `isoWeekKey` は同じ規則で実装してあり、年またぎを含む 400 日ぶんで一致を確認しています。

進行中の週・月はまだ増えるため、グラフでは薄く塗って「集計中」と表示し、増減の比較対象からも外しています。

**粘着度（DAU/WAU）** は「1 日あたりの平均利用者 ÷ その週の実人数」です。
100% なら全員が毎日、14% なら週 1 回ペース。定着の度合いを 1 つの数字で見るための指標です。

### 累計ダウンロードについて

ダッシュボードの「累計ダウンロード」は `totals/summary/installs`、つまり
**アプリを一度でも開いた端末の累計**です。App Store の実ダウンロード数とは一致しません。

- ダウンロードしただけで一度も開かなかった人は含まれない
- 「利用状況の記録」を OFF にした端末は含まれない
- 同じ人が 2 台に入れれば 2 と数える

App Store の正確なダウンロード数は App Store Connect の
「App Analytics」「Sales and Trends」で確認してください。
そちらを取り込むには App Store Connect API の秘密鍵が必要で、
公開リポジトリに置けないためこのダッシュボードには含めていません。

## 「回数」と「人数」の違い

同じ機能でも 2 通りの数え方をしています。

- **回数**（`events`）— ボタンが押された延べ回数。1 人が 10 回押せば 10。
- **人数**（`featureUsers`）— その機能を使った端末数。1 端末 1 日 1 カウントなので、同じ人が何度押しても 1。

回数だけを見ると「少数のヘビーユーザーが何度も押している機能」と
「多くの人が 1 回ずつ触った機能」が区別できません。
改善の判断には人数（＝どれだけの人に届いているか）が要るため、両方を並べています。

関連する操作は 1 つの機能にまとめています。たとえば「通知シートを開く」「通知を設定」「通知を削除」は、
どれも `bus_notif`（バス通知を使った）として 1 カウントです。
対応表はアプリ側 `AnalyticsService.featureOfEvent` と `catalog.js` の `FEATURES` にあります。

## ウィジェット

`WidgetCenter.getCurrentConfigurations` で「いま実際に置かれている構成」を 1 日 1 回読み、
種類・サイズ・個数を記録します。ウィジェットはアプリを開かずに使われるため、
セッション数や操作回数にはまったく表れません。ここだけが唯一の手がかりになります。

同じ種類を 2 つ置いていても 1 端末 1 カウントなので、「何人が置いているか」として読めます。
種類の合計が追加者数を超えるのは、1 人が複数種類を置いているためです。

## レポート（自動分析）

数字の読み方が分からなくても手がかりが掴めるように、直近の期間とその前の同じ長さの期間を比べ、

- 主要指標の増減表
- 伸びた機能 / 落ちた機能のトップ5
- そこから読み取れること（要対応 / 良い兆候 / 参考）
- 次にやるとよいこと

を日本語の文章として組み立てます。週次（直近7日）と月次（直近28日）を切り替えられ、
「レポートをコピー」でプレーンテキストとして書き出せます。

**生成 AI は使っていません。** しきい値と条件分岐だけで書いているため、同じデータなら必ず同じ文章になります。
API キーが不要で公開リポジトリのまま動き、卒制の考察に引用しても後から再現できます。

比較の単位を「今週（暦週）」ではなく「直近7日」にしているのは、
途中までの週を丸ごとの週と比べると、必ず減ったように見えてしまうためです。

## 計測している内訳の軸

| キー | 内容 | 備考 |
| --- | --- | --- |
| `model` | 機種（`iPhone18_3` → 「iPhone 17」に変換） | アプリの次回アップデート以降 |
| `versions` | アプリバージョン | |
| `osFull` | iOS バージョン（マイナーまで） | アプリの次回アップデート以降 |
| `os` | iOS メジャーバージョン | |
| `device` | iPhone / iPad の別 | |
| `display` | 画面サイズ区分 | アプリの次回アップデート以降 |
| `notif` | 通知の許可状況 | アプリの次回アップデート以降 |
| `dow` | 曜日（0=日曜、JST） | アプリの次回アップデート以降 |
| `lang` | 表示言語 | |
| `theme` | 表示モード | |
| `tenure` | インストールからの経過日数 | |
| `featureUsers` | 機能ごとの利用端末数 | アプリの次回アップデート以降 |
| `widgetUsers` | ウィジェット設置の有無 | アプリの次回アップデート以降 |
| `widgets` | 設置しているウィジェットの種類 | アプリの次回アップデート以降 |
| `widgetFamily` | 設置場所とサイズ | アプリの次回アップデート以降 |
| `widgetCount` | 1端末あたりの設置数 | アプリの次回アップデート以降 |

`daily` とは別に、実人数用のノードがあります。

| ノード | 内容 | 備考 |
| --- | --- | --- |
| `weekly/<yyyy-Www>` | その ISO 週の実人数と新規 | アプリの次回アップデート以降 |
| `monthly/<yyyy-MM>` | その暦月の実人数と新規 | アプリの次回アップデート以降 |
| `totals/summary/installs` | 初回起動した端末の累計 | 既存データから出せます |

いずれも「その日アプリを開いた端末」を1端末1日1カウントで数えた匿名の内訳です。
新しい軸はアプリ側の対応が要るため、それまでカードには「アプリのアップデート後に届きます」と表示されます。

機種名の変換表は `catalog.js` の `DEVICE_MODELS` にあります。
表に無い識別子は識別子のまま表示されるので、新機種が出ても表示は壊れません。新機種は 1 行足すだけで対応できます。

## デザイン

`制作物/web/DESIGN_RULES.md`（展示Web）と `制作物/app/ZONAVI/design.md`（アプリ）に従います。

- 書体：Futura（英数）＋ Noto Sans JP（日本語）。Futura はシステムフォントなので Google Fonts は Noto Sans JP のみ読み込み
- アクセント：`#294056`（ネイビー）
- ページ地：`#FCFAFA`、カードは白のフラット（影なし）、角丸は `DS.Radius`
- 余白は `DS.Spacing`（4 / 8 / 12 / 16 / 24 / 32）

### 意図的に変えたところ

| 項目 | デザインシステム | ここでの値 | 理由 |
| --- | --- | --- | --- |
| カード背景 | `#F5F5F5` | `#FFFFFF` | グラフ面としてコントラストが足りない。`#F5F5F5` はトラック等の二次面に回した |
| 薄いテキスト | `#9CA3AF` | `#71767F` | 白地で 2.5:1 しかなく、軸ラベルや構成比が読めない。4.6:1 の段に下げた |
| タブカラー | 予定 `#75C2A8` / リンク `#D98E1A` / 設定 `#9B72CF` | `#3BA385` / `#CB8621` / `#8E55CE` | データマークとしては彩度とコントラストが不足。**色相は保ったまま**（ずれ 0.5° 未満）明度と彩度だけ調整 |

ホーム `#6192DF` はブランド値のまま使えています。

配色は目視ではなく検証スクリプトにかけ、ライト・ダークとも全項目 PASS を確認しています。

```
カテゴリ配色（全ペア）  CVD ΔE 9.2 ／ 通常視 ΔE 15.3 ／ コントラスト 全色 3:1 以上
逐次配色（時間帯）      明度が単調 ／ 隣接 ΔL 0.06 以上 ／ 単一色相 ／ 明端 2:1 以上
```

ダークモードは自動反転ではなく、同じ手順でダーク面（`#1B1D21`）に対して選び直した別の段です。

### 折りたたみ

各セクションは `<details>` で開閉できます。スマホでは初期状態でサマリーとユーザー数だけを開き、
残りは畳んだ状態にします（縦に長くなりすぎるため）。開閉の状態は端末ごとに記憶します。

グラフは閉じている間は幅を測れないため、開いた時点でそのセクションだけ描き直します。
幅が足りないときは縮めずに横スクロールさせます（縮めるとラベルが読めなくなるため）。

## ファイル構成

```
index.html          画面の骨組み（セクションと操作 UI）
app.js              データ取得・集計・SVG 描画・CSV 書き出し・デモデータ生成
catalog.js          計測イベントのカタログ（iOS 側 AnalyticsEvent と 1:1 対応）
styles.css          デザイントークンとレイアウト
firebase-config.js  Firebase ウェブアプリの接続設定
```

Firebase SDK は `https://www.gstatic.com/firebasejs/10.14.1` から動的 import しているため、
npm install もバンドラも不要です。ローカルで開くときは ES モジュールの都合上、
`file://` ではなく簡易サーバー経由で開いてください。

```bash
python3 -m http.server 8000
# → http://localhost:8000/index.html?demo=1
```

## セキュリティについて

- `firebase-config.js` の `apiKey` は**秘密鍵ではなく**、ウェブに公開される前提の識別子です。
- 実際のアクセス制御は Realtime Database のセキュリティルールが行います。
  `analytics` ノードは許可された管理者メールアドレスでログインした場合のみ読み取れます。
- ダッシュボードが扱うのは匿名の集計カウンタのみで、UID・メールアドレス・端末 ID などの
  個人を特定できる情報は一切含まれません。
- アプリ側で「設定 → 利用状況の記録」を OFF にした端末は集計対象外です。

## GitHub Pages で公開する場合

1. リポジトリの **Settings → Pages** で、Source に `main` ブランチ（root）を指定します。
2. Firebase コンソール → **Authentication → Settings → 承認済みドメイン** に、
   公開される `<ユーザー名>.github.io` を追加します。これを忘れると Google ログインが失敗します。

`index.html` には `noindex, nofollow` を指定しているため、検索エンジンには載りません。

## イベントを追加したとき

iOS 側（`ZONAVI/Services/AnalyticsService.swift` の `AnalyticsEvent`）にイベントを追加したら、
`catalog.js` の `EVENTS` に 1 行足してください。日本語のラベル付きでダッシュボードに反映されます。
未登録のキーもキー名のまま表示されるので、取りこぼしは起きません。

内訳の軸そのものを増やす場合は、`database.rules.json` の `$group` の `.validate` にキーを足して
`firebase deploy --only database` する必要があります。これを忘れると書き込みがルールで弾かれ、
アプリ側を直しても数字が入ってきません。
